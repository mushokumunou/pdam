# Security model

Enforced by **Directus permissions**, not by prompts. Every claim below was verified against
`pdam.8w8.xyz` (Directus 12.6.1) by `scripts/verify_security.py` using real credentials for each
identity; the last run was **72/72 checks green**.

## 1. Principals

| principal | identity | trust |
|---|---|---|
| Administrator | `admin@8w8.xyz` (Administrator policy, `admin_access`) | trusted: schema, policies, permissions, deletion, upgrades |
| PDAM User | `pdam@8w8.xyz` (role + policy `PDAM User`, `app_access=true`) | semi-trusted human: Studio, dashboard, asset CRUD, archive; **no** hard delete, schema or access control |
| PDAM Agent | `agent@8w8.xyz` (role + policy `PDAM Agent`, `app_access=false`) | untrusted automation: REST/MCP, asset CRUD, archive; **no** Studio, delete, schema or policy changes |
| Public | unauthenticated | nothing: every business collection denies reads |
| Secret manager | external (Vaultwarden/Bitwarden/1Password) | owns passwords, TOTP seeds, keys, recovery codes |

The administrator is *not* a restricted super-user by design: Directus `admin_access` is
unrestricted, and trying to sandbox it would fake a boundary that does not exist.

## 2. Capability matrix (implemented)

| capability | Admin | PDAM User | Agent |
|---|---|---|---|
| Studio (Data Studio UI) | yes | yes | **no** (`app_access=false`) |
| Dashboard (Insights) | yes | yes | no (no permission on dashboards/panels) |
| Read assets + references | yes | yes | yes |
| Create / update assets | yes | yes | yes |
| Archive (`status=archived`) | yes | yes | yes |
| Hard delete assets | yes | **no** | **no** |
| Add / remove tags (junction rows) | yes | yes | yes |
| Read `asset_index` | yes | yes | yes |
| Write `asset_index` | technically yes* | **no** | **no** |
| Schema mutation (collections/fields/relations) | yes | **no** | **no** |
| Policy / role / permission mutation | yes | **no** | **no** |
| Dashboard / panel mutation | yes | **no** | **no** |
| Read other users | yes | self only (system rule) | **no** |
| Read project settings | yes | **no** | **no** |
| Read secret reference metadata | yes | yes | yes |
| Read secret material | n/a — never stored | n/a | n/a |

\* `asset_index` remains writable *in principle* for an administrator because Directus
`admin_access` bypasses collection permissions. It is a projection: writing to it by hand is a data
corruption bug, not a supported operation, and nothing in the product does it.

## 3. Policies as implemented

Generated by `scripts/apply_security.py` (idempotent) and captured by `d6s sync`:

| object | definition |
|---|---|
| policy `PDAM User` | `app_access=true`, `admin_access=false` — 49 permission rows |
| policy `PDAM Agent` | `app_access=false`, `admin_access=false` — 43 permission rows |
| role `PDAM User` → policy | via `directus_access` row |
| role `PDAM Agent` → policy | via `directus_access` row |
| user `pdam@8w8.xyz` | role `PDAM User`, password from `PDAM_USER_PASSWORD` |
| user `agent@8w8.xyz` | role `PDAM Agent`, static token from `PDAM_AGENT_TOKEN` |

**Effective access review** (permissions are additive; checked after creation, not assumed):

```
PDAM Agent   read 17 · create 13 · update 8 · delete 5
  read:   8 business collections + 5 tag junctions + asset_index + directus_collections/fields/relations
  create: 8 business collections + 5 junctions
  update: 8 business collections
  delete: the 5 junction tables only (required to remove a tag) — never an asset table
PDAM User    read 21 · create 14 · update 9 · delete 5
  = the agent set + directus_dashboards/panels/notifications/presets (Studio needs them)
  delete: the 5 junction tables only
```

There is exactly one access row per user (through its role); no user-scoped extra policy exists.

## 4. Secret boundary

PDAM stores **pointers**, never material.

Allowed: `secret_references.name`, `secret_type`, `provider`, `reference` (vault item UUID/path),
`vault_url`, `last_rotated_at`, `status`, `notes`; plus `accounts.secret_reference`,
`payment_methods.secret_reference` as FKs; `payment_methods.last_four` (four digits only).

Forbidden anywhere in PDAM: passwords, TOTP secrets, API tokens, private keys, recovery codes,
full card numbers, CVV, seed phrases.

Enforcement: `scripts/lint_secret_schema.py` scans both `templates/*.json` and the live Directus
schema of every asset/reference collection. It fails the build on a forbidden field name
(`password`, `api_token`, `private_key`, `totp_secret`, `recovery_codes`, `card_number`, `cvv`, …)
while allowing reference-shaped names (`*_reference`, `*_provider`, `*_type`, `reference`,
`last_four`, `vault_url`). `--self-test` proves the lint fires on real secret-material names and does
not fire on legitimate references.

Run it in any verification pass:

```bash
python3 scripts/lint_secret_schema.py        # exit 1 on violation
python3 scripts/lint_secret_schema.py --self-test
```

## 5. Public access

The Public policy has no permission on any business collection. Anonymous `GET /items/{asset_index,
vps, domains, accounts, subscriptions, payment_methods, secret_references, providers}` → **403**,
and anonymous `POST /mcp` → **401**. Verified per endpoint, not inferred from the UI.

## 6. Agent boundary details

- **No Studio**: `app_access=false`. The agent identity cannot load `/admin`.
- **No deletion**: no `delete` permission on any asset collection. `DELETE /items/vps/<id>` → 403.
  Archive is the supported "retire" operation (`PATCH {status:"archived"}`), and the projection
  follows it.
- **No schema/policy mutation**: `POST /collections`, `POST /fields/vps`, `PATCH /relations/...`,
  `PATCH /policies/...`, `POST /permissions`, `POST /roles`, `PATCH /dashboards/...`,
  `PATCH /panels/...` all → 403.
- **No privilege escalation**: `PATCH /users/<agent-id> {role:<admin>}` → 403; `/users` list → 403.
- **Discovery stays read-only**: `directus_collections`, `directus_fields`, `directus_relations`
  are readable so the agent can learn the model; they have no write permission.

## 7. MCP specifics (verified)

`/mcp` inherits the token's permissions, with two extra layers:

1. **Config layer** — `mcp_allow_deletes=false`: `items delete` answers
   "Delete actions are disabled" before any permission check.
2. **Permission layer** — with `mcp_allow_deletes` temporarily enabled, the same delete still fails
   with a permission error. Layer 1 is a convenience; the permission is the actual boundary.

`collections`/`fields`/`relations` MCP tools answer **"You must be an admin to access this tool"**
for the agent, even though it has read permission on those collections.

**Pitfall (recorded for callers):** `items update` without `keys` and without a `query.filter`
updates **every row** of the collection. Always scope writes:

```json
{"action":"update","collection":"vps","keys":["<uuid>"],"data":{"region":"Osaka"}}
```

During verification this was observed live (two test rows were updated by an unscoped call); the
data was restored, and both scoped forms (`keys`, `query.filter`) were re-tested and update exactly
one row.

## 8. Credential handling

- Credentials never enter git: `.admin-token`, `.agent-token`, `.pdam-user-password`, `.env` are
  git-ignored; `d6s` does not sync users (opt-in feature left off), so tokens cannot leak through
  the sync files.
- `scripts/apply_security.py` reads `PDAM_USER_PASSWORD` / `PDAM_AGENT_TOKEN` from the environment;
  when absent it generates a value and writes it to a `0600` file locally, printing only a notice.
- The server-side env file `/opt/stacks/pdam/.env` is `0600`.
- Scan performed on the working tree **and** git history for the admin password, JWTs, Cloudflare
  and GitHub token prefixes, and private-key headers: **0 hits**.

Rotation procedure if a token is ever exposed: issue a new static token
(`PATCH /users/<id> {"token": "<new>"}`), write it to the runtime secret store, revoke the old value,
re-run `scripts/verify_security.py`. For the human account change the password in Studio.

## 9. Verification

```bash
python3 scripts/verify_security.py     # 72/72 expected
python3 scripts/lint_secret_schema.py  # secret-material lint
```

The script uses three real identities (agent static token, human login, anonymous) and prints
`PASS/FAIL` per check with expected vs actual HTTP status. Any "expected deny → allowed" exits 1.

## 10. Known limitations (12.6.1)

1. **Row-level permission rules are licence-gated** on this instance
   (`custom_permission_rules_enabled` is a restricted resource). Permissions are therefore
   collection-level only: no per-row filters, e.g. "agent may only update assets it created".
   Consequence: "update everything" is possible for an allowed collection; see the MCP pitfall above.
2. **`directus_users` has a built-in system permission** scoped to `$CURRENT_USER`, so any signed-in
   human can read their own profile (correct) but not others (verified 403).
3. **`PATCH /roles` with `policies`** expects `directus_access` ids, not policy ids, and answers 403
   when given policy ids. Bind roles to policies through `POST /access` (what the script does).
4. **`mcp_allow_deletes`** only disables the MCP tool; it is not a permission system.
5. Directus surfaces a `RESTRICT` foreign-key violation as **HTTP 500**, not 409 (see
   `data-model.md` §17).

## 11. Not in this phase

Secret-manager integration (Vaultwarden API, credential resolution), agent CLI/MCP wrapper,
per-row ABAC, TFA enforcement, IP allow-listing. `secret_references` remains metadata only.
